# Invented v2 hospital API → real staging API mapping

Scope: `src/features/receptionist`, `src/features/lab-scientist`, `src/features/hospital-admin` (and their `src/mocks/*.ts`).
Profile query (`GET /api/auth/staff/profile`) and `src/features/staff` excluded, as are radiologist calls.

Sources: `docs/api/openapi.json` (fetched 2026-11-21), the v1 app (`C:\Users\USER\Desktop\DocuHealth-`), and live
GET probes against staging on 2026-11-21 (roles: receptionist, lab, lab_admin, admin, nurse). No writes were sent,
so **every POST/PATCH/PUT mapping below is from the schema and v1 code only, not tested**, including whether the role
is allowed to call it.

Status key:

- **MATCH**: a real endpoint does the job. The response needs reshaping (renames, `null` for avatar etc.) but every field the UI needs has a source.
- **PARTIAL**: a real endpoint covers the core of it, but some UI fields or behaviour have no source, it takes several calls, or the request shape is different.
- **NONE**: no endpoint does it.

## Cross-cutting facts (apply to all three features)

- **IDs.** Real resources use `sqid` strings. Patients are addressed by **HIN** (`/api/patients/{hin}/…`), so the UI's `patient.id` should become the HIN everywhere. No endpoint exposes an opaque patient id.
- **Pagination.** Lists are DRF-style: `?page=&size=` → `{count, next, previous, results}`. The UI schemas expect `{items, total, page, pageSize, counts}`, so the adapters have to rebuild that. Per-tab `counts` always need one call per tab (`size=1`, read `count`).
- **Sex.** The API's `gender` enum is `male|female|other|unknown`. The UI uses `male|female|prefer_not_to_say`, so map `other`/`unknown` → `prefer_not_to_say` when reading. When writing, `prefer_not_to_say` has to go out as `unknown` (or `other`). Decide which.
- **Names.** The API returns `firstname`/`lastname`/`middlename`, and the UI wants `name`. Staff come as `*_info {sqid, firstname, lastname, role, specialization}`. Build "Dr. X" yourself; there is no title field.
- **Avatars.** No patient or staff object has an avatar/photo URL, so every `avatarUrl` is `null`.
- **Spec drift seen live.** `patient_info.payment_provider` is typed `string` in the spec but is really an object `{type: "private"|"hmo"|"company", provider, member_id, updated_at}`. Lab `items_info[].result_info` is typed `string` but is really an object, or `null` before a result exists. Some GETs have no response schema at all: `dashboards/*`, `lab/dashboard`, `hospital-ops/patients`, `patients/{hin}/payment-category`.
- **Ignored query params.** `GET /api/hospital-ops/patients` silently ignores `ward` and `ordering`; tested, the counts and order did not change. `GET /api/lab/dashboard` ignores `start_date`/`end_date`; same numbers came back. `GET /api/auth/staff` ignores `is_active`, `status` and `is_admin`. Only `role`, `search`, `page` and `size` work.
- **Periods.** Several UI views take `period` (today/week/month). Only these real endpoints take a time window: `hospital-ops/appointments*` (`scheduled_time_gte/lte`) and `dashboards/hospital` (`start_date/end_date`).
- **Unread counts.** Unread notification and message counts have no endpoint in any feature. This is already a TODO in all three profile schemas.
- **Admin flag.** `GET /api/auth/staff/profile` has no `is_admin`. Only the login response carries it (`acting_as[].is_admin`). The lab scientist vs lab admin split depends on it.

### Receptionist: gaps for the backend

1. **Reception metrics.** Extend `GET /api/hospital-ops/dashboards/receptionist` (or add an endpoint) with `total_check_ins`, `checked_in_today`, `waiting_in_queue`, `appointments_today` and their changes against the previous period, taking `start_date/end_date` like `dashboards/hospital`.
2. **Reception queue.** Add a receptionist-readable check-in list (or confirm `hospital-ops/patients?status=outpatient` is meant for this) with `reason`/visit purpose and a `status` that says waiting vs with nurse vs with doctor. Allow searching by HIN.
3. **Check-out permission.** Confirm a receptionist may `POST /api/hospital-ops/check-ins/{sqid}/close`, or add a receptionist check-out endpoint.
4. **Appointment reschedule and cancel.** Add `POST /api/hospital-ops/appointments/{sqid}/reschedule {scheduled_time, note}` and `…/cancel {reason, details}` for receptionists, notifying the patient. Or confirm the receptionist may use `PATCH …/{sqid}/assign` for rescheduling.
5. **Single appointment.** Add `GET /api/hospital-ops/appointments/{sqid}`.
6. **Appointment ↔ check-in link.** Add arrived/checked-in state on appointments (or a `check_in` reference) so the UI's `arrived/checked_in/in_progress` statuses have a source.
7. **Booking without choosing staff.** Either make `staff` optional on `appointments/book` (front-desk/unassigned booking), or the UI must add a doctor picker.
8. **Slots.** Hospital appointment capacity (`open_slots`, `total_slots` for a date range) for the calendar summary, or the design drops those numbers.
9. **Search by HIN** on `GET /api/hospital-ops/appointments` (and a `patient=<hin>` filter), so a profile can show the upcoming appointment.
10. **Front-desk patient profile.** A receptionist patient endpoint (or extend `/api/patients/{hin}/details`) with `last_visit {at, department}`, `last_check_in {at, status}`, `upcoming_appointment`, `assigned_doctor`, visit history (check-ins + appointments, with in/out times), `dependants[]` and `proxies[]` (with relationship, dob, gender, last visit), and a photo URL.
11. **Doctor follow-up requests.** An endpoint for doctors to request a follow-up appointment and for the front desk to list (per patient) and confirm/cancel them. Nothing exists today.
12. **Link an existing patient as a dependant** (`POST /api/patients/{hin}/dependants` with an existing child HIN), and clarify what `confirmed_by` should contain (enum?).
13. **DOB at desk signup** is required, but the v2 patient form doesn't collect it. That's a UI change, not a backend ask, unless the backend can relax it.
14. **Coverage values.** API `company` vs UI `nhis`: agree on one list.
15. `GET /api/records/patients/{hin}/soap-notes/shared` returns **500** for the receptionist (ValueError). Bug report.

### Receptionist: real endpoints the v2 UI doesn't use yet

- `POST /api/hospital-ops/check-ins {patient: <HIN>}`. **This creates the actual check-in.** The v2 "Check-in patient" dialog only looks the patient up and links to the profile; nothing checks them in (v1 called this after the HIN lookup).
- `GET /api/hospital-ops/admissions/requests?status=pending|accepted|rejected&search`, `PATCH …/requests/{sqid}/accept`, `PATCH …/requests/{sqid}/reject {rejection_reason}`. The front desk's bed-request queue (v1 had it). Live: pending 0, accepted 47, rejected 48.
- `GET /api/patients/payment-providers?category=hmo|company&search` and `PUT /api/patients/{hin}/payment-category {type, provider?, member_id?}` (body from v1; the spec has no body schema). Lets the desk set a patient's HMO/company coverage. Live GET: 200.
- `GET /api/hospital-ops/wards` (bed availability; v1 receptionist home showed bed/ward totals). Live: 200, 8 wards.
- `POST /api/auth/signup/upgrade` and `/complete`: give a dependant their own account.
- `POST /api/hospital-ops/appointments/{sqid}/close`: close (complete) an appointment. Only staff with the same role as the booked staff may, so probably not the receptionist.
- `GET /api/hospital-ops/patients?status=inpatient|inpatient_discharge|outpatient_discharge`. The receptionist can read these (v1 had a receptionist patient-management page).

## 2. Lab scientist (`/hospital/lab/*`)

Counts: **MATCH 0 · PARTIAL 10 · NONE 1** (11 calls)

**The big structural difference.** A real lab order (`sqid`) has several **items** (`items_info[]`), one per test. Each item has its own `status`, specimen time, rejection and result, and each test has several **parameters** (each with its own LOINC and range). The v2 UI treats one order as one unit with one `stage` and one result. Every action endpoint is **per item** (`/test-orders/{sqid}/items/{item_sqid}/…`). Either the UI acts per item, or the adapter loops over the items.

Real item statuses: `pending`, `sample_collected`, `in_progress`, `result_ready`, `result_accepted_by_lab_admin`, `result_accepted_by_doctor`, `rejected`. Order `aggregate_status` values seen live: `in_progress`, `partial_ready`, `all_rejected`. The full list is not in the spec.
Stage mapping: UI `pending`←item `pending`; `in_progress`←`sample_collected|in_progress`; `completed`←`result_ready|result_accepted_by_lab_admin|result_accepted_by_doctor`; `rejected`←`rejected`.
